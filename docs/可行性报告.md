# 微信视频号直播流获取可行性报告

> 目标：把微信视频号里的足球赛事直播保存到本地，用于个人战术/赛事分析。
> 日期：2026-11。结论基于公开资料、社区实测与本地验证；标注了"未验证"的部分请自行实测。

---

## 0. 结论

**技术上完全可行，且有一条风险最低的路线：利用微信自带的"投屏到电视"功能，在局域网里伪装一台 DLNA 电视，拿到直播 m3u8 地址，再用本地录制器分片落盘。**

三条现实路线，按推荐顺序：

| 路线 | 做法 | 适合 | 主要代价 |
| --- | --- | --- | --- |
| **① 投屏捕获（推荐）** | 伪装 DLNA 电视，接收 `SetAVTransportURI` 里的 m3u8 | 手机 + 同一 WiFi，不想动微信 | iOS 可能走 AirPlay 搜不到；不是所有直播间都能投 |
| **② 代理抓包** | PC 微信 + 系统代理 + 根证书（如 wx_channels_download） | 有 Windows/Mac，要顺手 | 装证书、改系统代理、跟进微信版本 |
| **③ 屏幕录制** | OBS 窗口捕获 / scrcpy / 采集卡 | 兜底，任何情况都能用 | 画质有损、无法后台、占用一台机器 |

**合规边界（重要）**：微信协议明确禁止用第三方工具抓取客户端与服务器之间的数据，可导致封号；体育赛事画面另有版权（腾讯系 NBA/CBA/英超监测最严）。**自己录、自己看**属于个人学习研究的灰色空间，风险最低；**一旦公开传播或商用，几乎必然侵权**。详见第 7 节。

## 1. 视频号直播到底是怎么发流的

### 1.1 形态

| 项目 | 结论 | 证据强度 |
| --- | --- | --- |
| 协议 | HLS（m3u8 + TS 分片）为主，也存在 HTTP-FLV | 项目实测（投屏截获示例为 `pull-l1.wxlivecdn.com/...m3u8`） |
| 域名 | 直播走 `*.wxlivecdn.com`（部分 CDN 为 `flv*.wxqcloud.qq.com`）；点播是另一套 `finder.video.qq.com` | 社区实测 |
| 地址 | 每次开播重新签发，带时效签名，**没有固定房间号**可拼 | 项目文档 |
| 有效期 | 没有公开数值；工具作者一律按"会过期"处理 | 未知 |
| 加密 | 直播 TS 分片通常不加密；点播 mp4 才是加密 + key 解密 | 项目实现差异 |

> 注意：网上大量"视频号下载"教程讲的是**点播视频**的解密（`encfilekey`/`token` 那套），和**直播**不是一回事。直播的地址是投屏/播放时动态下发的，不能靠房间号构造。

### 1.2 清晰度与帧率

- 观众端档位：蓝光 / 超清 / 高清 / 标清。
- 推流能力上限：1080×1920、≤60fps、≤10000kbps（腾讯云视频号推流模板）；但官方推流指引的建议值是 **1080p / 30fps / 3000kbps**，说明 60fps 是上限而非常态。
- 社区估算码率：标清 ~1M、高清 ~2–3M、超清 ~4–5M、蓝光 ~6–8M。
- **判断：国内足球赛事在视频号多为 1080p30。** 战术分析够用；高速镜头会有运动模糊。若主播推 60fps，档位里能看到 `FRAME-RATE`，可用 `probe` 确认。
- 投屏是否降档：DLNA 只传 URL，码率由服务端决定；视频号是否对投屏设备降档**没有公开证据**，需实测对比。

### 1.3 地址失效的表现

- 播放列表请求返回 403/404；
- ffmpeg 报错退出（`Error opening input` / `Server returned 403`）；
- 录制文件停在某个分片不再增长。

因此**"一个 URL 从头录到尾"不能假设成立**，必须按"会过期、可续"来设计。

## 2. 五条获取路线对比

| 维度 | ① 投屏捕获 | ② 代理 MITM | ③ 逆向 Hook | ④ 模拟器 + root | ⑤ 屏幕录制 |
| --- | --- | --- | --- | --- | --- |
| 代表工具 | 本项目 / [wechat-finder-dlna](https://github.com/gtoxlili/wechat-finder-dlna) | [wx_channels_download](https://github.com/ltaoo/wx_channels_download) | Frida/Xposed 脚本 | 安卓模拟器 + 抓包 | OBS / scrcpy / 采集卡 |
| 平台 | 任意（同局域网） | Windows/macOS（文档称也有 Linux 构建） | 特定版本 | Windows/Linux | 任意 |
| 是否改微信 | 否 | 否（但装根证书、改系统代理） | 是（注入进程） | 是（root 环境） | 否 |
| 获取内容 | 原始流地址 | 原始流地址 | 内存里的地址 | 原始流地址 | 屏幕像素 |
| 画质 | 原始（可能被投屏降档） | 原始 | 原始 | 原始 | 有损（取决于窗口大小/编码） |
| 账号风险 | 极低（标准投屏协议） | 中（改网络环境，有风控案例） | 高（注入/Hook，2025 年有大规模封号） | 高 | 无 |
| 维护成本 | 低（协议稳定） | 中（微信改版会打断，需跟版本） | 高（版本一更新就挂） | 高 | 低 |
| 长时录制 | 好（可重投续录） | 好（有续传） | 一般 | 一般 | 差（需一直前台） |
| 硬限制 | 需手机、需直播间支持投屏 | 需 PC 微信、需信任证书 | 需 root/越狱 | 性能差、易被检测 | 无法后台、分辨率受限 |

补充事实：

- 投屏入口：手机微信直播间右上角「…」→ 投屏（2021 年上线，需同一 WiFi）。**PC 微信没有内置 DLNA 投屏**，所以投屏路线必须用手机。
- **不是所有直播间都能投**：付费直播可能禁止录屏/投屏；也有用户反馈某些微信版本投屏入口消失（个例，未复现）。
- **[wx_channels_download](https://github.com/ltaoo/wx_channels_download)** 是目前维护最勤的代理方案：自动装证书、注入下载按钮、直播下载（标注实验性）、边下边播、断点续传，依赖 ffmpeg。新版微信改版会导致按钮消失，需要跟 release 更新。
- **没有公开证据表明视频号媒体域强制证书钉扎**——否则代理方案早就整体失效；真正的麻烦是页面结构变化和风控，而不是 pinning。

## 3. 推荐方案：投屏拿地址 + 本地分片录制

### 3.1 为什么是这条路

1. **不碰微信进程、不装证书、不改系统代理**——从微信视角这就是一台普通电视，协议层没有可检测的东西；
2. **地址是微信自己给的**，不是逆向出来的，微信改版也不影响；
3. 拿到的是**原始拉流地址**，画质是原始档位（除非服务端对投屏降档）；
4. 断流可以靠"再投一次屏"续上，这对 90–120 分钟的足球赛很关键。

### 3.2 本仓库做了什么

`wxcap`（`live_capture/`）把这条链路做成了两个命令：

```
python3 -m live_capture dlna --record recordings/match01
```

- `dlna.py`：SSDP 组播宣告 + UPnP 设备描述 + SOAP 控制/事件，完整实现 MediaRenderer 的
  `SetAVTransportURI` / `Play` / `GetTransportInfo` / `GetPositionInfo` 等动作，让手机认为投屏成功；
- 捕获到地址后写入 `captures/current_url.txt`，并回调启动录制；
- `recorder.py`：两种后端
  - **hls**（m3u8 默认）：自己解析播放列表，按 `EXT-X-MEDIA-SEQUENCE` 增量下载，支持 `AES-128`、`EXT-X-DISCONTINUITY`，分片丢了会记 `gap`，地址 403 会等新地址并**按序号续录**；
  - **ffmpeg**（FLV/未知格式）：`-c copy` + 按时间切片 + 断线重连；
- 输出 `part-*.ts`（每 10 分钟一个）+ `index.jsonl`（分片级时间轴）+ `recording.json`（摘要），结束时自动无损转 mp4。

### 3.3 为什么不能只用一句 `ffmpeg -i URL out.mp4`

| 问题 | 后果 | 本项目的处理 |
| --- | --- | --- |
| 地址过期 | ffmpeg 直接退出，整场只录到一半 | 检测 401/403，等重新投屏，按序号续录 |
| 单文件写入 | 进程崩溃/断电，mp4 的 moov 写不进去，整个文件报废 | 10 分钟一个 part，最多损失一个 |
| 分片短暂丢失 | 音画时间轴悄悄错位 | `index.jsonl` 记录每个分片的 seq/时长/断点 |
| 直播结束 | 需要人工判断 | `EXT-X-ENDLIST` / 长时间无新分片自动收尾 |
| 加密分片 | ffmpeg 能处理但不可控 | 纯 Python 解密，逻辑透明 |

## 4. 录制参数建议（足球场景）

### 4.1 存储估算

| 档位 | 码率 | 1 小时 | 90 分钟 |
| --- | --- | --- | --- |
| 高清 | 2–3 Mbps | 0.9–1.4 GB | 1.4–2.0 GB |
| 超清 | 4–5 Mbps | 1.8–2.3 GB | 2.7–3.4 GB |
| 蓝光 | 6–8 Mbps | 2.7–3.6 GB | 4.1–5.4 GB |

建议预留 **每场 6 GB**，并保留 `part-*.ts` 直到确认 mp4 可播放。

### 4.2 参数模板

```bash
# 开赛前 5 分钟启动，避免错过开场
python3 -m live_capture dlna \
  --name "分析机" \
  --record recordings/2026-11-17_A队_vs_B队 \
  --quality best \
  --segment-seconds 600 \
  --max-duration 9000
```

- `--max-duration 9000`（2.5h）防止忘记停止导致挂机；
- `--quality best` 拿最高码率；如果磁盘紧张用 `--quality 720` 或 `--quality 超清对应档位序号`（先 `probe` 看）；
- 别用 `--start edge`：会丢掉投屏瞬间已经缓冲的 10–30 秒。

### 4.3 双保险

对重要场次，建议**同时**开一路屏幕录制（OBS 窗口捕获，720p 即可）作为兜底：投屏失败/中途地址彻底失效时，至少还有一份低码率素材。

## 5. 录制之后：分析工作流

```bash
cd recordings/2026-11-17_A队_vs_B队

# 1) 校验成片
ffprobe -v error -show_entries format=duration,size -show_entries stream=codec_name,width,height,avg_frame_rate recording.mp4

# 2) 按事件切片（无损，秒级）
ffmpeg -ss 00:32:10 -to 00:33:40 -i recording.mp4 -c copy clip_goal.mp4

# 3) 单帧（画战术板用）
ffmpeg -ss 00:32:15 -i recording.mp4 -frames:v 1 -q:v 2 frame_goal.jpg

# 4) 每秒 2 帧批量抽帧
mkdir -p frames && ffmpeg -i recording.mp4 -vf fps=2 frames/%06d.jpg

# 5) 缩略图拼版（快速浏览全场）
ffmpeg -i recording.mp4 -vf "fps=1/15,scale=320:-2,tile=5x4" -frames:v 1 contact_sheet.jpg

# 6) 提取解说音频做转写
ffmpeg -i recording.mp4 -vn -ac 1 -ar 16000 audio.wav
```

`index.jsonl` 的用途：每行有 `t`（抓取时的 Unix 时间）、`seq`（HLS 分片序号）、`duration`。
如果有多路信号（比如另一台机器录了不同机位），可以用 `t` 做粗对齐，用画面里的计时器/比分牌做精对齐。

## 6. 官方开放能力：没有

- 视频号助手 API 只有直播记录、预约、大屏数据、留资、电商数据，**不提供拉流地址或回放文件**（[官方文档](https://developers.weixin.qq.com/doc/channels/api/channels/)）。
- 小程序 `channel-live` / `getChannelsLiveInfo` 只能在小程序内嵌播放，返回 `feedId`/`nonceId`/状态，不给 URL。
- 自家直播：视频号助手 RTMP 推流（推流地址 2 小时有效），回放可在助手"单场数据 → 直播回放"下载——但**只对你自己开的直播有效**。
- **结论：对"别人的赛事直播"不存在合法拉流 API。** 合法路径只有拿到主办方授权、成为该场次运营方，或让对方直接给回放文件。

## 7. 合规与风险

### 7.1 平台协议

腾讯规则明确禁止：复制、修改、增加、删除、挂接运行或创作任何衍生作品（包括使用插件、外挂、第三方工具）、爬虫/模拟下载、规避安全措施等，可导致**限制功能直至永久封号**（[腾讯规则](https://rule.tencent.com/rule/62049e9c-bd24-4a3c-93e4-9c227d790422)）。

- 投屏路线不修改微信、不注入、不代理流量，**落在协议风险最低的一档**，但仍属于"第三方工具录制"。
- 代理/证书/Hook 路线风险更高；社区有"自动化挂机录三天被限制登录""mitmproxy 抓流被判异常登录"的案例（[CocoLoop 讨论](https://www.cocoloop.cn/t/topic/3154)），但没有可核实的"仅因投屏录制被封"的官方案例。
- 建议：**不要用主号长时间挂机**；控制频率；重要账号与新工具分开。

### 7.2 版权

- 体育赛事画面通常有独立版权。国内执法很重：NBA 诉抓饭案 2025 年判赔 3000 万、首例认定平台与主播分工合作直接侵权；CBA 诉 B 站案天价索赔（[己任解读](https://www.genlaw.com/cn/index.php?c=show&id=766)）。
- 个人自录自看，落在著作权法"为个人学习、研究或者欣赏"的合理使用空间，**风险低**；
- 一旦上传、分享、二次剪辑发布、用于商业分析产品，**几乎必侵权**，且体育版权方监测最积极。

### 7.3 建议的自我约束

1. 只录自己有权观看的公开直播；
2. 只存本地，不进网盘、不发群、不上传平台；
3. 分析产出（截图、数据）避免大段还原原画面；
4. 商用/对外服务前，先拿授权。

## 8. 待验证清单（拿到机器后按顺序做）

| # | 验证项 | 通过标准 | 失败时的 Plan B |
| --- | --- | --- | --- |
| 1 | 手机微信直播间 →「…」→ 投屏，能否看到 `wxcap 电视` | 列表里出现设备 | 换 Android 手机；检查同一 WiFi / AP 隔离 / 组播 |
| 2 | 点击投屏后终端是否打印地址 | 出现 `捕获到投屏地址` | 看日志是否收到 SOAP；可能是 AirPlay 设备，换安卓 |
| 3 | `probe` 该地址 | 打印码流列表（1080p 等） | 抓包/代理路线 |
| 4 | 录 3 分钟并播放 | 音画同步、可拖动 | 换 `--backend ffmpeg` / `--quality` |
| 5 | 中途让地址失效（等 30–60 分钟）再重投 | 自动续录，`recording.json` 里 `url_refreshes>0` | 手动 `record` 接续 |
| 6 | 录满一场 90–120 分钟 | 无内存/磁盘泄漏，part 正常滚动 | 缩短 `--segment-seconds` |
| 7 | 对比投屏画质与手机端 | 确认是否降档 | 若降档，考虑代理路线拿原始档 |

---

## 9. 一句话总结

**能录，而且不用碰微信。** 用"假电视"骗过投屏拿到 m3u8，再自己分片录制、断流重投续录，是当前个人赛事分析场景里风险最低、维护成本最低的解法；代价是必须有一台同局域网的机器和一部能投屏的 Android 手机，且要接受 1080p30 的素材质量。
